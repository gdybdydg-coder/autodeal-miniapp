## Що змінено

Планувальник використовує вільні слоти для інших належних перевірок після
резервування основного пошуку й оцінювання. Максимум чотири паралельні операції,
планові дедлайни, квота, epochs і claims збережені.

Падіння старого тесту із сімома одержувачами досліджено: сім Delivery були
збережені, три вже надіслані, чотири чекали незалежного dispatcher. Dispatcher
надіслав усі сім. Тест тепер перевіряє збережені записи та реальну незалежну
доставку, а не завершується разом зі старим drain-helper.

Спільне джерело двох публічних сторінок `/uk/last/hour/` працює з окремою датою
додавання. Початкова база збережена о 18:33:16 UTC; перезапуск її не скинув.
Старі й рекламні картки відсіюються. Самої появи ID, зміни ціни чи дати оновлення
недостатньо. Користувач явно погодив свіжі повторні публікації під старим ID за
наявності доказу нової дати додавання; це не дозвіл на старий каталог.

Чинна версія спочатку завершує всі чотири вибрані основні операції, а потім
може перевірити одного кандидата через API не частіше разу на 15 секунд.
Обмеження зберігається після перезапуску. Основні pending-оцінювання, помилки
пошуку, catch-up або відставання курсора понад подвійний інтервал
(мінімум 120 с) блокують цей додатковий крок. Основні операції не витісняються.

API підтверджує категорію легкового авто, активність, актуальну додатну ціну,
відповідність дат і збереженим фільтрам. Далі створюється одне спільне завдання
офіційного AI-оцінювання. `confirmed_deals_only=true`, minDiscount, /stop,
activation epochs і всі sent/uncertain claims діють. Відсутні необов'язкові
поля та ремонт/пошкодження самі по собі не блокують авто; чинні виключення
закордонних авто й потреби розмитнення збережені.

Naive-дати мають явне трактування Europe/Kyiv. HTML і офіційний API повинні
дати ту саму секунду; неоднозначні DST-часи відхиляються. Офіційна документація
не визначає часовий пояс naive addDate, тому це задокументоване припущення,
а не встановлення початкової дати чи дій продавця.
