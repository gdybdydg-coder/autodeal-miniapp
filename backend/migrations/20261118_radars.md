# Radar schema migration 20261118_radars_v1

## Release scope and activation

This is an in-place update of the existing backend and Mini App frontend, using
the existing database, domain, Telegram bot, authentication, billing and worker.
It does not require a new service, queue, database, bot or paid dependency. This
document describes a prepared release; it is not evidence of production deployment.

`Settings.env()` defaults `RADAR_ENABLED` to `true`. Direct construction of
`Settings` defaults it to `false` for legacy tests. On an existing deployment,
startup applies the migration before starting workers. The persisted version
marker is authoritative: setting `RADAR_ENABLED=false` after migration does not
reactivate legacy searches, routes or execution. A missing/failed schema activation
must fail startup rather than silently restore the old search path.

`backend.radar_migration.migrate(engine)` runs in one transaction before workers.
PostgreSQL serializes concurrent startups with a transaction-scoped advisory lock.
The version row makes subsequent applications no-ops. No legacy table is dropped.

New normalized tables: `radars`, `radar_brands`, `radar_models`, `radar_regions`,
`radar_search_bindings`, three catalog tables, `radar_schema_versions`, and the
one-time `radar_legacy_search_states` activation backup.

Each real radar occupies one unique `(user_id, slot)` with a database check that
slot is 1, 2 or 3. Configuration writes and derived executor replacement use a
single transaction and the same User row lock as Telegram delivery. Foreign keys
enforce ownership and selected-model relationships. Price categories use a lower
inclusive, upper exclusive bound; category 6 has no upper bound.

The migration creates **zero radars**. All existing users therefore receive three
empty slots. Old Search configurations remain in the database, disabled, with
their prior enabled state captured. In-flight legacy scans are paused. Users,
Telegram IDs, payment requests, entitlements, billing histories, admin settings,
listing cache and delivery receipts are not deleted or reset.

Catalog records come only from verified AUTO.RIA dictionary identities already
held in SourceCache or the versioned `backend/data/radar_catalog_seed.json` snapshot.
Expired dictionary rows may supply stable identities, never prices or valuations.
Radar configuration endpoints do not consume API quota or refresh dictionaries.
An unavailable model dictionary is reported explicitly; selecting all models for
that official brand remains valid. A completely missing catalog fails closed.

The checked-in official public dictionary snapshot contains 397 brands, 5,070
models and 25 regions (24 oblasts plus the Autonomous Republic of Crimea), using
AUTO.RIA identifiers. The two regions absent from the live public states response
retain their documented official IDs: Luhansk 17 and Crimea 21. No model dictionary
is loaded from a paid API during UI configuration or monitoring. Snapshot updates
are controlled releases: verify provider IDs, completeness and ambiguous names,
run import/relationship tests, then merge records without deleting referenced
catalog identities. Updating the JSON alone does not rerun an applied migration;
a future refresh must be explicit and versioned.

## API and execution contract

Every endpoint uses the existing signed Telegram WebApp identity. User IDs in
request bodies never select ownership.

- `GET /api/radars`: three-slot overview and actual subscription access.
- `POST /api/radars`: create a paused radar; optional `client_request_id` makes
  mobile retries idempotent for that user and creation payload.
- `PUT /api/radars/{id}`: edit configuration with the current revision.
- `PATCH /api/radars/{id}/status`: explicitly pause/resume with a revision.
- `DELETE /api/radars/{id}?revision=N`: delete after frontend confirmation and
  immediately free the slot.
- `GET /api/radars/catalog?brand_id=N`: local catalog, with models for that brand.

Configuration stores official brand/model/region IDs. Empty `region_ids` means
all Ukraine; empty `model_ids` for a selected brand means all its models. Price
categories are `[0,2000)`, `[2000,5000)`, `[5000,10000)`, `[10000,15000)`,
`[15000,20000)` and `[20000,infinity)`. Integer provider query limits may be
broader, but the local final price check remains upper-exclusive. Years are
inclusive and validated on both sides. A radar accepts exactly one threshold
from 5, 10, 15, 20, 30, 40 or 50 percent.

Maximum eligible listing price is the confirmed AUTO.RIA lower market boundary
multiplied by `0.95 * (1 - radar.min_profit / 100)`. This reuses the existing
valuation infrastructure, including its conservative five-percent reserve; it
does not replace it with a second arithmetic implementation. Confirmed AUTO.RIA
valuation must be available (`RIA_AI_PRICE_ENABLED=true` with existing server-only
credentials). Unvalued or merely informational listings do not become Radar deal
notifications. No secrets belong in frontend configuration or this document.
Live monitoring without that valuation setting fails configuration validation
before the initial migration. This is the existing authenticated AUTO.RIA API
range, not a new claim that its values equal the website's visual range. Final
delivery also verifies the provider-range evidence rather than accepting a
legacy peer-price estimate when a process is misconfigured.

Users without a subscription may create, edit, pause and delete their radars.
Resume requires actual unexpired access and a started Telegram conversation.
Expired active radars persist as `subscription_expired`; renewal after a lapse
does not automatically resume them. An extension observed before the current
expiry can retain uninterrupted access. Current access, radar revision/epoch,
configuration and delivery deduplication are checked again before sending.

Each radar generates derived existing Search executors through
`radar_search_bindings`; it does not introduce a second polling service. Compatible
executors share existing discovery feeds and cached listing/valuation work. The
planner conservatively merges lossless unions (including adjacent price ranges)
and retains individual final filters. Frozen pagination, retries and quota state
remain intact. This reduces requests for compatible radars; it is not a claim to
find a globally minimal request plan across arbitrary multidimensional filters.

## Production cutover and rollback

Before production activation, snapshot the database and verify dictionary coverage,
slot concurrency, legacy-disable behavior, and existing billing/Telegram tests on
an isolated PostgreSQL instance. The migration itself retains all old tables.

Drain/stop the old monitoring executor before applying the versioned migration.
Old application binaries do not know the Radar marker and must not overlap with
the new worker during a rolling cutover. Prevent old configuration writes during
that window, deploy the matching backend and frontend to their existing services,
then verify the migration version, zero migrated radars, preserved account/billing
counts, new three-slot UI and a single healthy worker before reopening monitoring.
Keep the existing API limits and current schedule; a schema release is not
permission to spend extra quota or change polling cadence.

The existing service supports this two-deployment cutover without a new service:

1. Preserve the existing environment and enable `RADAR_CUTOVER_HOLD=true` before
   deploying the reviewed Radar commit to the existing backend. The factory then
   returns a standalone maintenance application. It does not construct normal
   settings, connect to the database, migrate, start any billing/source/delivery
   tasks or make Telegram requests. Only `GET /health` returns 200; every other
   method/path returns a Ukrainian 503 and `Retry-After: 60`, including the webhook.
   This is an intentional short pause of billing/API access and webhook handling;
   updates must be retried, not acknowledged and discarded.
2. Verify `/health` identifies the expected commit and `maintenance: true`.
   Its configuration booleans expose presence/enabled state only, not credentials
   or successful connections. Existing `MONITOR_ENABLED`, `DELIVERY_ENABLED`,
   `SOURCE_READY` and `RIA_AI_PRICE_ENABLED` should be true for the subsequent live
   activation; existing AUTO.RIA key/user ID must be configured. Preserve all
   request ceilings, schedule settings, database and Telegram credentials.
3. Wait for provider evidence that the old instance finished shutting down, and
   check the retained monitor/source leases and delivery outcomes. A successful
   health response, `Live` label or lease age alone does not establish that the
   old executor stopped. Never steal/reset a lease, claim, uncertain send or
   request counter to make the cutover appear idle. Take the database snapshot
   after the old process has drained, including billing, claims and receipts.
4. Set `RADAR_CUTOVER_HOLD=false` and deploy the **same reviewed commit** with
   `RADAR_ENABLED=true`. The preceding instance is maintenance-only, so it cannot
   race migration or edit/delete newly derived Search executors. Normal startup
   runs the migration before its single existing monitoring worker. Verify the
   migration version, three empty slots, preserved data counts and worker health
   on the existing URLs. No radar is automatically created or resumed.

The hold defaults to false and takes precedence over `RADAR_ENABLED` and an already
persisted migration marker. It can temporarily stop a migrated deployment without
reactivating legacy execution. Its health response is deliberately **not** a
database check or evidence of working monitoring. Remove the hold after a verified
cutover; leaving it enabled keeps all user and webhook endpoints unavailable.

Rollback must stop/drain the Radar worker first, retain a full snapshot including
new radars and receipts, then restore the pre-migration application/database state
as a coordinated operation. Merely switching an environment flag is insufficient:
the persisted migration marker intentionally prevents legacy jobs from restarting.
Never restore historical enabled flags while Radar delivery is running; doing so
could introduce parallel discovery and duplicate alerts. Existing billing and
delivery records must not be rolled back to an earlier snapshot after new payments
or notifications have occurred. Prefer a forward fix once Radar has real activity.

## Verification evidence

The backend Radar suite has 80 passing cases, including migration rollback and
repeatability, all price boundaries, ownership, subscription transitions, retry
idempotency, official full-seed import and transaction-local catalog resolution.
The two legacy schedule regression files have 52 passing cases after aligning
their stale assertions with the already-deployed three-hour night interval.
The isolated PostgreSQL harness additionally checks concurrent first migration,
eight competing radar creations yielding exactly three slots, foreign keys and
preserved billing/receipt state. Application integration and browser checks are
recorded by the release owner in `test-results/radar/`; consult the final result
manifest for exact commands, timestamps and full-suite totals. These local test
results do not constitute a live production alert or deployed-release proof.
The separate cutover suite verifies that the hold never calls normal application
startup, database setup, migration, source acquisition or Telegram transport;
all non-health paths are rejected and normal startup is unchanged without the flag.
